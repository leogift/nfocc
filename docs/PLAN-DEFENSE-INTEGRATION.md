## 二、逐项：缺什么、谁给、怎么接

### D1 车身掩码 —— 只缺一份多边形

**代码状态**：完全就绪。`NFFrameInput.body_mask` 与 `NFPipelineConfig.body_mask`
都已存在，`nf_mask_rasterize_polygon()` 已实现并测过（矩形面积 768 = 理论值）。

**缺的输入**：车体俯视轮廓多边形，单位 mm，车体系。

| 需要的东西 | 格式 | 谁能给 |
|---|---|---|
| 车体轮廓多边形顶点 | `[(x,y), ...]` mm，顺时针 | 整车尺寸图，或标定时量测 |
| 该多边形相对相机光心的位置 | 已含在车体系坐标里 | 与 `NFPose.t` 同一基准 |

**接入步骤**（约半天，无需外部等待）：

1. 在 `nfocc_default.h` 加一组默认多边形顶点（先用矩形 5000×2000 占位）；
2. `nfocc_run` 启动时调 `nf_mask_rasterize_polygon` 生成 mask（一次，缓存）；
3. 每帧 `in.body_mask = cached_mask`；
4. 判据：`NFLutStats.d4_body_mask` 计数非零，且 BEV 车体轮廓一圈的假点消失。

**风险**：矩形占位会**过度屏蔽**——真实车体有后视镜、轮眉凸起，
用矩形会把车体外的有效区域也剔掉。量产前必须换成真实轮廓。

**结论：D1 不需要外部支持就能跑通，但"跑通"用的是占位矩形，不是真实车体。**

---

### D2 双向一致性 —— 需要引擎支持反向匹配

**代码状态**：`nf_occlusion_weight(d_fwd, d_bwd, tau, lambda)` 已实现并测过。

**缺的输入**：`d_bwd` —— 反向视差图，即**把右图当左图再匹配一次**得到的视差。

| 需要的东西 | 现状 | 谁能给 |
|---|---|---|
| 反向匹配能力 | **引擎不支持** | 需改 `engine_sgbm.cpp` |
| `NFEngineConfig` 增加方向选项 | 无 | 我改 |

**为什么现在接不了**：`nf_engine_run(eng, &lv, &rv, &dr, &dm)` 里
`lv/rv` 是调用方给的。理论上把两图交换再跑一次就行，但：

1. `NFDisparityRange.b_mm` 的符号语义要跟着反（左图变了，视差方向反）；
2. SGBM 输出 `d` 恒为正，反向时真实视差应为负，需要显式取反；
3. 计算量翻倍（35.5 ms → 71 ms），需评估预算。

**方案**：
```
正向: nf_engine_run(g→右图, d→左图)  -> d_fwd
反向: nf_engine_run(g→左图, d→右图)  -> d_bwd_raw, 取 -d_bwd_raw
对每个像素: w = nf_occlusion_weight(d_fwd[x], d_bwd[x+d_fwd[x]], tau, lambda)
w < w_min 的点 == 遮挡/误匹配, 剔除
```

**外部支持需求：无。** 纯代码改动，约 2 天。

**代价**：耗时翻倍。若预算紧张，可只在**近场视口**（前后 90° 那两个）开启，
左右 150° 视口用 SGBM 自带的 `uniqueness` 近似。

### D4 双基线交叉验证 —— 需要第二条基线的点

**代码状态**：`nf_voxel_verify_cross(ctx, x, y, z, source_bit, thresh_mm, verdict)`
已实现。

**缺的输入**：同一物点用**第二条基线**重算出的位置。

| 当前有什么 | 缺什么 |
|---|---|
| 一个 `t_cam`（相对上一参考帧的位移） | 第二个 `t_cam`（隔更远的帧） |
| `NFFrameInput.frame_gap` 单值 | 两套参考帧各自的原图与位移 |

**关键发现**：D4 与双基线状态机是**同一个问题的两半**。
`NFBaselineManager` 已经在维护长/短两个参考帧，`nf_voxel_verify_cross`
需要的第二条基线就是它给的。所以**先接双基线，D4 才有输入**。

**方案**：
```
双基线状态机给 (t_short, ref_short) 与 (t_long, ref_long)
  -> 用 t_short 跑一遍体素化, 得点集 A
  -> 用 t_long  跑一遍体素化, 得点集 B
  -> 对 A 中每个点调 nf_voxel_verify_cross(该点在 B 里的位置)
```

**外部支持需求：无外部数据，但需要 `NFPose` 的绝对位姿。**

当前 `t_cam` 只有**相对位移**，且来自 `ego_distance` 标量（该序列忽略横摆，
yawRate 0.43°/s）。`NFBaselinePose` 需要 `R[9] + t[3]` 的**绝对**位姿。

| 项 | 现状 | 需要 |
|---|---|---|
| 绝对位姿 | 无 | 上游给里程计位姿（轮速+IMU 融合） |
| 姿态角 | 无 | 至少 yaw 积分 |

**这是唯一真正需要外部支持的地方**：要接双基线 + D4，上游必须提供
**带姿态的绝对位姿**，而不只是帧间位移标量。

**降级方案（无需外部）**：假设纯平移、yaw 由 `ego.yaw_rate × dt` 积分。
该序列 yawRate 0.43°/s、5 Hz，每帧 0.086°，10 帧累计 0.86° —— 可接受。
但急转向或打滑时会失效，**只能算原型验证，不能量产**。

## 三、汇总：外部支持清单

| 项 | 是否需要外部支持 | 具体是什么 | 没有时的降级 |
|---|---|---|---|
| D1 车身掩码 | **需要**（但可用占位） | 车体俯视多边形顶点 | 矩形 5000×2000 占位 |
| D2 双向一致性 | **不需要** | 只需改引擎 | — |
| D4 交叉验证 | **需要** | 带姿态的绝对位姿 | yaw_rate 积分，仅原型 |
| 双基线状态机 | **同上** | 同上 | 同上 |

**一句话**：三项里，**D2 现在就能做**；D1 能跑但用的是假车体；
**D4 + 双基线卡在"上游只有帧间位移标量、没有带姿态的绝对位姿"**。
