# 摘要

NFOCC 是一套面向边缘计算平台的多相机鱼眼近场稠密感知系统。输入 4 路 1280×966 鱼眼图像，输出车辆周边 0.5–5 m 的点云与 2D 高程柱（zMap），目标硬件是 RK3588 与 Axera M57。它不依赖激光雷达或超声波，深度来自**自车运动产生的视差**——同一台相机在两个时刻看同一物体，帧间位移就是基线。

系统的技术路线由两个物理事实决定。第一，每一路鱼眼都是**单视点单目**，单帧无深度，只能靠运动双目；基线与车速成正比，5 km/h、5 Hz 时只有 278 mm，深度误差按 Z² 增长。第二，纯前向平移会**结构性破坏** SGBM：像移从 FoE 辐射、跨 FoE 方向翻转，水平视差搜索失去意义。因此系统分成两条测距路径：侧向用 SGBM 视差 + 射线三角化，前向用径向膨胀的解析解 `Z = Σ[(u×v)·(t×v)] / Σ‖u×v‖²`。

工程上是 C++11 的 C 接口实现，核心库 11,004 行（src + include），除 vcam 静态库外不链接第三方库，引擎经函数表晚绑定，相机投影统一走 vcam。主链包含 4 路视口 LUT（规划 6 视口）、工况门控、双基线状态机、D1/D3/D4 防御、σ 逐点传播与 80 cm 硬截断、Hash + CMA 体素融合、zMap/zIndex 柱状压缩、五阶段稠密体素精简，以及网格哈希 + DBSCAN 的离线聚类。

**本次复核（2026-11-09）的结论是：链路已打通，精度未证实，性能有一处硬缺口。** 21 个 ctest 目标通过 20 个，177 个用例、2,343 次断言中只有端到端深度精度的 4 个用例失败。真实数据上：

- STEREO 路径有效帧 **104 ms**，在 5 Hz 的 200 ms 预算内，余量 48%；
- FORWARD 路径有效帧 **11.2 s**，超预算 56 倍，是当前最大的工程缺口；
- 稳态内存 **151–170 MB**，解析预算 291 MB，余量约 45%；
- 真实数据单帧产出 2,077 点，但 z 最小 **−498 mm**（车体高度，地面以下约 0.5 m）；2,077 点中 **236 点（11.4%）** 低于地面 100 mm，cam0 占 212 点，问题集中在前向路径；
- 侧行 5 km/h 的分段深度中位误差为 **291 / 256 / 433 / 896 mm**，四段全部未达 150 / 200 / 320 / 320 mm 的验收线。

因此这份报告不把"功能覆盖率"当成"可交付"。业务链路、算法、工程化都已完成到能跑真实数据的程度，但**精度没有可信测量**：唯一测精度的用例失败，真实数据又没有点云真值。能否交付，取决于精度验收，而不是代码行数。

# 一、项目定位与业务逻辑

## 1.1 为什么做近场

远距有毫米波和激光雷达覆盖，0.5–3 m 的贴地区域反而是盲区：停车桩、路缘石、低矮障碍、车头正下方的儿童，都在这一段。超声波能测距但没有稠密形状，环视相机有图像但没有深度。NFOCC 要做的是用已有的 4 路鱼眼，补上这段**稠密、带不确定度、可给规划直接用**的几何。

产出不是一张深度图，而是两类下游结构：带来源与 σ 的点云（15 字节/点，`NFPoint`），以及按底面网格压缩的高程柱（10 字节/点，`NFDownstreamPoint` + zMap/zIndex）。前者给调试与可视化，后者给 15,000 点配额的下游接口。

## 1.2 运动双目：速度就是基线

四路鱼眼各自是单目，同一时刻没有视差。深度只能来自自车运动：上一帧与当前帧构成一对虚拟双目，基线是这段位移。

帧间位移由车速和帧率决定：

```
b = v / f_frame         5 km/h @5 Hz -> 278 mm
                        9 km/h @5 Hz -> 500 mm
                       15 km/h @5 Hz -> 833 mm
```

视差与深度的关系是 `d = f·b/Z`，误差传播为：

```
σ_Z = Z²·σ_d / (f·b)        （忽略 2% 的里程计尺度项）
```

FIG_PHYSICS

这个式子决定了三件事。**第一，误差随距离平方增长**：同样 0.5 px 的匹配误差，1 m 处只有 1.3 cm，5 m 处就是 33 cm。**第二，基线越长越准**：把 278 mm 换成 833 mm，5 m 处误差从 328 mm 降到 109 mm。**第三，低速是物理下限**：5 km/h 时基线只有 278 mm，再怎么调 SGBM 参数也变不出基线。

图 1 是计算值。150 mm 验收线在 5 m 处要求 `b ≥ 607 mm`（σ_d 固定 0.5 px），约等于 11 km/h；若坚持 833 mm 基线，则要求 `σ_d ≤ 0.34 px`，比 SGBM 的典型值 0.3–0.5 px 还紧。两条路都说明：**150 mm @ 5 m 在 5 km/h 下不可达，是几何边界，不是实现缺陷。**

## 1.3 三档工况与两条测距路径

系统按帧间位移和运动方向分档，不同档位走不同算法。分档的目的不是"覆盖更多场景"，而是避免在物理上测不出的工况里输出假点。

| 工况 | 判据 | 处理 | 原因 |
|---|---|---|---|
| 静止 / 极慢 | b < 278 mm | FROZEN_NEAR，不产出 | 视差 < 1 px，测不出 |
| 侧向运动 | σ = \|t_xy\|/\|t\| ≥ 0.80 | STEREO：SGBM + 三角化 | 极线与图像横轴夹角大，水平搜索有效 |
| 前向运动 | σ ≤ 0.35 | FORWARD：径向匹配 + 解析测距 | 纯前向平移下 SGBM 结构性失效 |
| 中间带 | 0.35 < σ < 0.80 | HYBRID，实际仍走 STEREO | 过渡区，未做双路融合 |
| 超长基线 | b > 833 mm | FROZEN_FAR，重置 | 重叠视场不足，匹配陡崩 |
| 急转 / 丢帧 | Δyaw > 15° 或 gap 超限 | FROZEN_ROT / GAP，重置 | 旋转不产生视差 |

833 mm 的上限不是拍的：它由 `numDisparities=256` 与最近可测距离反推，参数改动必须同步重算（`nf_params_validate` 的 R2/R6 检查会拒绝不自洽的配置）。

**为什么前向必须另走一条路。** 纯前向平移时，所有像移都从 FoE（运动极点）辐射出去；越过 FoE，像移方向翻转。SGBM 假设"右图 = 左图沿 x 平移"，这个假设在 FoE 附近失效。实测证据是（2026-11-02 视差探针，本次未复测）：合成墙面理论视差 140.8 px，SGBM 输出 2.2 px；偏置随基线严格成正比（278 mm 时 −34 px，556 mm 时 −61 px），说明它锁到了固定的错误周期，不是随机噪声。换参数、换窗口、换唯一性阈值都无效，因为问题不在参数。

前向路径用径向膨胀：在视口图上沿 FoE 方向做一维搜索，得到两帧的视线方向 u、v，再用闭式解求距离。这个式子对任意平移方向成立，不需要极线平行，也不需要迭代。

## 1.4 输出契约：冻结不是空

四种冻结状态下，`nf_pipeline_process` 返回 `num_points=0` 与对应的 `NF_E_BASELINE_*` 状态码，而不是返回一个空点云。下游必须能区分"这一帧没结果"和"这一帧没有障碍"。

这个语义在工程上比看起来重要。早期版本冻结时返回错误码、不发消息，下游把"车停下来了"当成"系统挂了"。现在冻结也发完整消息，只是 `is_frozen=1`、点数为 0。

冻结与失效语义（下游视角）：

| 状态码 | 触发条件 | 下游看到什么 | 建议动作 |
|---|---|---|---|
| `NF_E_BASELINE_IDLE` | b < b_min 或历史不足 | `is_frozen=1`，点数 0 | 保持上一帧，不报警 |
| `NF_E_BASELINE_OVER` | b > b_max | 同上 | 重置基线队列 |
| `NF_E_BASELINE_ROT` | 两帧 yaw 漂移 > 15° | 同上 | 等直行后恢复 |
| `NF_E_BASELINE_DEGRADED` | 位姿降级 / 长丢帧 | 同上 | 降级到短基线 |
| `NF_E_EXTRINSIC_INVALID` | 该路外参自检失败 | 该路 `cam_status` 置位 | 禁用该路并告警 |
| `NF_E_ENGINE_RANGE` | `numDisp < d_max` | 该路无输出 | 检查 R2/R6 参数 |

输出结构分两条路并存：`cloud` 是全量 `NFPoint`（15 字节/点），给调试与可视化；`dvf_points` 是精简后的 `NFDownstreamPoint`（10 字节/点，≤15,000），配 `dvf_zmap/zindex` 给下游 O(1) 柱查询。另有逐路 `mode/cam_status` 与整帧 `is_frozen`。

# 二、系统架构与代码调用

## 2.1 四层与硬边界

代码分四层，职责边界是硬的：应用层只做参数解析和接线，主链层负责调度、门控和生命周期，算法层是无状态纯函数或显式上下文，基础设施层管相机模型、内存和 IO。

FIG_ARCH

三个设计决定值得单独说：

**核心库不链接 OpenCV / ZeroMQ / onnxruntime。** `nfocc_core` 只依赖 vcam 静态库（内部件，单独编）；SGBM 由 `nfocc_engine_sgbm` 单独编成库，经 `NFEngineOps` 函数表在 `nfocc_run` 侧注入。这样核心库可以单独交叉编译、单独做单元测试，也避免了"SGBM 换实现要重编整个工程"。

**相机投影只有一条路。** 原生 `nf_cam_project/unproject` 已删除，投影与反投影统一走 vcam 静态库。vcam 不可用时编成桩，返回 `NF_E_ENGINE_UNSUPPORTED`。这消除了"两套公式各算各的"这一类最难查的偏差。

**Stage 同步，Pipeline 决定并发。** 单个 stage 内部不带线程池，并发只在 pipeline 层按相机维度开（目前只并行 warp）。原因是要保证同输入两次调用逐位相同，录包重放不能漂。

## 2.4 调用关系

一次 `nf_pipeline_process` 的调用顺序（对应 `pipeline.cpp`）：

# 三、数据流 Pipeline

## 3.1 单帧链路

FIG_PIPE

数据流的形状是"输入 → 视口重采样 → 工况决策 → 两条测距路径二选一 → 逐点防御 → 体素融合 → 导出 / 精简 → 输出"。两条路径的产物都是车体系 3D 点，之后共用同一套防御、体素和输出代码；这是刻意的，否则前向与侧向会得到两套不一致的点云。

关键点：

**warp 是唯一并行的阶段。** 它读原图 + LUT、写自己的视口缓冲，没有共享写状态，OpenMP 4 线程安全。SGBM 串行，因为每路工作内存大，4 路并行会超上板预算。

**所有缓冲在 init 期分配。** 视口图（每相机 2 张当前/参考）、有效性掩码、视差图、点云、DVF 的三块输出（zmap / zindex / dvf_pts）都是创建期一次分配、运行期复用。目的是消除长时间运行的堆碎片与 P99 毛刺。

**前向与侧向的中间量分开。** 前向用 `m_pts/m_conf/m_valid`，侧向用 `dmap`。共用一块缓冲会让"前向产出的点"和"侧向产出的视差"互相污染。

## 3.2 前处理：视口 LUT

4 路鱼眼的畸变极大，直接在原图上做匹配，极线既不平行也不水平。NFOCC 的做法是构建 6 个虚拟针孔相机（左右各 150°，前后各两个 90°，共 6 个视口），每个视口有理想的内参，LUT 记录"视口每个像素对应原图哪个像素"。

当前主链实际使用 **4 路 1024×475、150°×120°、f=137.19** 的视口。前后各两个 90° 视口的规划表在 `nfocc_viewplan.h` 里，但主链是"每相机一个视口"，尚未做到"每相机同时两个视口"；`--viewplan` 只是把前后视口整体偏转 ±45°，不是 6 视口并行。

LUT 每像素 5 字节（u/v 各 Q12.4 的 int16 + valid u8），无效点写 0xFFFF 哨兵，不能用 (0,0)——那是合法的左上角像素。构建期有四道有效性检查：超出图像、超出有效半径、超出 `max_theta`、被车身掩码剔除。

**车身掩码 D1** 在 LUT 构建期就把车身像素标为无效，零运行时代价。方向是对的，但当前实现是矩形投影占位：实测 MVL 挖掉 76.6%、MVR 挖掉 77.3% 的画面（把天空、建筑、路面一起挖了），而 FV 只挖 0.1%（车头几乎没盖住）。负对照：开启掩码 2,077 点，关闭 2,089 点，只差 12 点。**掩码既过又漏，当前对最终点云几乎没有作用。**

## 3.3 后处理：σ 传播、截断与精简

每个点带自己的空间不确定度，由真实视差与真实基线算出，不是常数：

```
Z    = f·b/d
σ_Z  = sqrt( (f·b/d² · σ_d)² + (Z · σ_b)² )
```

`σ_d=0.5 px`，`σ_b=2%`。实测分档：1 m 处约 2 cm，5 m 处 34 cm，8 m 处 85 cm。`NFPoint.sigma_cm` 用 u8 存，255 是"不可知"哨兵，聚合时取最小值（多次观测里只要有一次特别准，就按准的算）。

**σ 硬截断 80 cm** 丢弃超过门限的点。作用不是"去掉远处"，而是去掉"测量不可信"的点：SGBM 锁错周期时视差极小，`Z=f·b/d` 会让深度爆炸，同时 σ 按 `1/d²` 膨胀，正好被这个门限识别。按 σ 截断比按距离截断更有依据——后者会误杀"远处但测量可靠"的点。

**五阶段精简 DVF** 是可选后处理，把稠密点压到下游 15,000 点配额内，同时剥掉地面、保留外壳。细节见 4.8。

# 四、算法详解

## 4.1 相机模型

支持两种鱼眼模型：

- **KB**：`r = f·(θ + k1θ³ + k2θ⁵ + …)`，只有奇次项，焦距单独给。
- **径向多项式**：`ρ(θ) = k1θ + k2θ² + k3θ³ + k4θ⁴`，含偶次项。**k1 就是小角度等效焦距（px/rad），不是畸变系数**。hanqtech FV 的 k1≈339.75，若当 KB 的 k1 用，θ>0.2 rad 处投影完全失真。

主点不是 `cx_offset`，而是 `cx = width/2 + cx_offset − 0.5`。四路实测主点 641.3–646.2，图像中心 640；`cx_offset` 只有 1.8–6.7 px 量级。

vcam 后端与模型定义式的对拍（单测 `test_vcam_bridge`）：radial_poly 比较 388 点，最大偏差 **8.1e-5 px**；KB 比较 400 点，最大偏差 **1.3e-4 px**。判据是 0.5 px（σ_d 的全部预算），实际差了三个数量级。

## 4.2 视口 LUT 的几何

视口是**虚拟针孔相机**，按 `pitch=0、roll=0、只有 yaw` 构造。真实相机的安装角只决定"这个车系方向落在哪张鱼眼的哪个像素"，不参与视口朝向。所有视口共面，融合时体素才能对齐，也才能与下游 ego 系 BEV 直接比对。

前后视口用 90° 而不是 150°，是"用覆盖换角分辨率"：同样基线 278 mm，f=295 的 5 m 处视差 16.4 px，f=137 只有 7.6 px。前后各有 ±45° 两个视口，是为了直行时获得**横向基线**——单个正前视口的横向基线为 0，纯前向平移下视差深度在结构上消失。

视口的环带是**绝对俯角 10°–60°**，不是相对光轴。真实 FV 俯角 22.7°，两种解释差 540 mm 的地面距离：相对光轴看到 432 mm（车头正下方），绝对俯角看到 973 mm。后者才是近场要的。

## 4.3 运动双目的几何

两帧构成虚拟双目。设参考帧光心 O0、当前帧光心 O1、物点 P，射线 u、v，平移 t：

```
q0 = Z·u,  q1 = q0 − t,  q1 ∥ v
```

三角化用两射线的叉积闭式解，float32 下误差 5e-6。前向路径不用 `Z=f·b/d`，因为该式只在平移垂直于视线时成立；前向工况视线与平移夹角 0–90°，光轴附近误差可达 10.3 倍。

**左右图顺序是一个真实踩过的坑。** 侧行时参考帧在车系 y−278、当前帧在 y=0，而视口 x 轴 = 车系 −Y，所以参考帧在视口 x 的正方向——**参考帧才是"左图"**。反了之后 1–2 m 中位误差 259→223 mm、2–3 m 495→380、3–4 m 935→511、4–5 m 1383→601，样本数还少 6%（代码注释记录的历史实测）。

**镜像模式**用于另一侧：对应点是 `(w−1−x)+d`，不是 `x−d`。传错时剔除率看着正常（1–9%），点数掉 97%。（这是两帧、已知位移的 motion stereo，不是完整 SfM。）

## 4.4 两条测距路径

**侧向 SGBM。** 参数 `numDisp=256, blockSize=5, uniqueness=10, speckleWindow=100, downscale=2`。`d_max` 由基线与该档最近距离反推：`d_max = f·b/Z_min`（Z_min=500 mm）。契约是：`numDisp < d_max` 返回 `NF_E_ENGINE_RANGE` 且不写输出；无效像素必须由 valid 掩码标出，不得用 `disp=0` 表示无效；同输入两次调用逐位相同。

IMG_DISP

**前向径向。** `nf_match_radial` 沿 FoE 方向做一维搜索，得到两帧视线 u、v，再调用 `nf_forward_range`：

```
Z = Σ[(u×v)·(t×v)] / Σ‖u×v‖²
```

这个式子对任意平移方向成立，不需要极线平行。输出是距离 |q0|，不是光轴深度 q0.z——混用会差数倍。之后用 D3 FoE 锥过滤：平移方向 8° 半角内的点深度退化，直接丢弃，否则会解出几十米外的"拉丝"。

合成单测 `forward_range_exact` 用 6 个距离点（500–3000 mm）验证，全部通过。真实直行数据走这条路径，有效帧 11.2 s，耗时在径向标量搜索，不在解析解本身。

## 4.5 门控与双基线状态机

FIG_GATE

默认门控 `nf_gate_decide` 是无状态的：只看当前帧相对上一参考帧的位移，按 `frame_gap → b_min → b_max → σ` 的顺序分流。它的问题是低速时帧间位移刚好在 b_min 附近，会频繁在 STEREO 与 FROZEN_NEAR 之间震荡，形成"周期性感知静默"的锯齿。

双基线状态机改为累积多帧：维护一个 16 帧的环形队列，同时保存短基线与长基线。`|t_long| ≥ b_target(500 mm)` 时用长基线输出并晋升；`|t_long| > b_max(833 mm)` 或 `|Δyaw| > 15°` 时重置。单测连续跑 10 帧：短基线 1 次、长基线 8 次、冻结 1 次，基线从 278 升到 556 mm，精度约提升 1.8 倍。

但状态机只按 `|t|` 判，**不判方向**。直行数据 b 到 500 mm 时会被判成 STEREO，而 SGBM 在纯前向平移下失效：实测 46,821 次插入、最终 0 点（全部越界）。同一数据用默认门控判 FORWARD，产出 2,077 点。这是当前状态机的一个真实设计缺口，不是实现 bug；修法是加 σ/FoE 方向判据，或只对侧向相机启用。

D4 的门限不能固定 50 mm：2 m 处短基线自身的 σ 就有 66 mm，固定门限会把长基线的有效点一起衰减。实现用 `τ = max(tau_min, 2·sqrt(σ1²+σ2²))`，2 倍覆盖约 95%，近场有 50 mm 下限兜底。实测开启 D4 时，单帧"融合 15,095 次、残差超限 16,312 次"，最终点数与关闭时相同（2,077）——说明在这份稀疏点云上，D4 主要在同一个体素内做多次观测的融合/衰减，而不是改变点数。这正是设计意图，不是"开了没效果"。

D2 的缺失意味着遮挡断裂带没有专门防护。NEW_MOD §0.1 建议接 SGBM 自带的 `disp12MaxDiff`，只多一次反向匹配，成本远低于完整 D2。

## 4.7 体素融合与 zMap

体素网格 200 mm，ROI x ±9 m、y ±7.5 m、z −0.5–2.5 m，共 90×75×15 = 101,250 格；哈希表 262,144 槽（2^18），开放寻址线性探测。

每个体素维护质心、有效观测数 `n_eff`、来源位图、最小 σ：

```
c_n = c_{n-1} + w·(p − c_{n-1}) / (n_eff + w)
n_eff += w
```

`w` 是置信度（0–1），`n_eff` 超过上限时衰减一半，防止旧观测永久压制新观测；质心钳位在体素内 ±vox/2，同点重复插入漂移 < 1 mm。

索引是 `ix = (X_MAX−X)/vox`、`iy = (Y_MAX−Y)/vox`（**X/Y 反向**，为了与原始 NFOCC 的 Hash 位序一致），`iz = (Z−Z_MIN)/vox`。柱体编号是 `cell = iy·nx + ix`，不是 `ix·ny+iy`；用错会让高程图转置，方阵测试测不出来。

zMap 是 `uint32` 位图，bit k = 第 k 层存在；zIndex 是前缀和，下游用 `col` 在 O(1) 内取到该柱的所有点。bit31 恒 0，nz=15 时只用 bit0–14。

## 4.8 五阶段稠密体素精简

FIG_DVF

每帧可产 10 万–50 万点，直接送下游有三个问题：15,000 点配额、70–80% 是平坦路面、墙/车体内部是实心。DVF 用五阶段整数/位运算把它们压成外壳：

1. **AABB + FoE 锥**：ROI 裁剪 + 方向锥。判据 `dot>0 && dot² ≥ (x²+y²)·cos²(15°)`，只用乘法与比较，无开方、无三角函数。
2. **柱体位图**：每个 `(X,Y)` 一个 uint32，记 32 层占用。
3. **地面剥离**：CTZ32 找最低层，剥掉连续两层；但"剥完上面还有东西"才算地面，纯地锁（孤立 1–2 层）保留。
4. **极坐标外壳**：720 扇区（0.5°/扇区）、30 cm 壳厚，只保留每个方向的首击表面。
5. **配额熔断**：近场优先 + 两遍计数排序，上限 15,000。

实测单帧 2,077 → 1,534（AABB）→ 1,361（FoE）→ 1,356（地面）→ 1,352（外壳）→ 1,352（配额未触发）。15 万合成点 1.83 ms，输出 2,070 点。

## 4.9 聚类与动静分离

聚类对外接口叫 `nfocc_octree.h`，实现是**纯网格哈希**，不是八叉树。理由是六次迭代的教训：树结构要维护父子链、节点 CSR 区间、哈希叶编号三套结构的一致性，任何一处不同步就表现为"查不到"或"段错误"，而根因离得很远。纯网格哈希只有一个结构 `(ix,iy,iz) → 点列表`，逻辑上不可能不一致。

格边长 120 mm（= eps），查询恰好覆盖 3×3×3=27 格。150k 点均匀分布实测：构建 6.1 ms，DBSCAN 54.1 ms，256 簇、噪声 73,136；极密团簇 258.7 ms，25 簇。DBSCAN 的核心点判据天然拒绝噪声——密团 + 200 孤立点的用例输出 1 簇 + 200 噪声，而体素连通域会输出 200 个假目标。

动静分离分两层：点级速度（本帧点变换到上一帧坐标系找最近邻，除以 Δt）与簇级投票（一簇内动态点占比 >50% 判动态）。位姿补偿的方向写反过一次：正确是 `P_prev = Rᵀ·P_cur + t`，不是 `Rᵀ(P_cur − t)`。负对照守住了这条——不给位姿时静止墙的速度是 3,080 mm/s，给位姿后是 0。

真实数据上，1,255 点聚出 84 簇、噪声 917、最大簇只有 5 点。**算法正确，但点密度不足以聚出物体。** 根因还是精度/点数，不是聚类。

# 五、关键特性与亮点

这一节只列"能指向一次对照实验或一条实测值"的特性，不列设计意图。

**1. 不增加传感器，用运动换深度。** 4 路鱼眼是已有件，深度来自自车位移。代价是低速精度受限，收益是零硬件增量。基线分档 278/500/833 mm 对应 5/9/15 km/h，是"可测"与"不可测"的硬边界。

**2. 前向解析测距，而不是硬套视差公式。** `Z = Σ[(u×v)·(t×v)]/Σ‖u×v‖²` 对任意平移方向成立，合成单测 6/6 通过。这条路径解决的是 SGBM 在纯前向平移下的**结构性失效**，不是"精度稍差"——实测墙面 140.8 px 真值输出 2.2 px，属于匹配失败。

**3. 双基线晋升。** 单测从 278 mm 升到 556 mm，连续 8 次长基线输出；按 σ∝1/b，5 m 处误差从 328 mm 降到 164 mm（计算值）。

**4. 物理化的不确定度，而不是固定门限。** 每个点带 σ，按 L2 严格传播；80 cm 截断切的是"不可信"，不是"远"。1 m 2 cm、5 m 34 cm、8 m 85 cm。

**5. 全整数/位运算的精简器。** 15 万点 1.83 ms，输出 ≤15,000，10 字节下游点。阶段 4 必须回原始点数组取坐标（位图恢复不出 `sqrt(x²+y²)`），这条写进了代码注释，防止后人"优化掉"。

**6. 确定性与零拷贝。** 同输入两次调用逐位相同（单测）；ZMQ 接收侧不 memcpy，直接把 `zmq_msg_data()` 交给解析，发送侧用 `zmq_msg_init_data` 转移所有权，省掉 ZeroMQ 内部第二次拷贝。

**7. 负对照是工程习惯，不是补丁。** 车身掩码开/关（2,077 vs 2,089）、D4 开/关（融合 15,095 / 拒绝 16,312）、动静分离给/不给位姿（0 vs 3,080 mm/s）、里程计有无 yaw_rate（3,000 vs 2,700.9 mm）、左右图顺序（误差 1,383→601 mm）。这些对照让"代码跑了"和"逻辑生效"能分开。

**8. 文档与代码同仓、可自检。** 42 篇文档，`tools/docs_check.py` 检查交叉引用、参数唯一、索引、符号登记，当前全绿；`scripts/verify_docs.sh` 还做"文档说已接入的，代码里确实有调用"的双向校验。

失败原因至少两层，且都已定位：合成场景只有地面 + 一面墙，纹理是规则周期函数，SGBM 会锁错周期；探针的采样又全部落在 700–800 mm 的近场地面，这段本来就不适合 SGBM。**但这只能解释"为什么这个测试失败"，不能证明真实精度达标。** 真实数据没有点云真值（只有 24 张图 + 36 个 json，含 ego_distance / ego_yawRate，没有深度），所以真实精度目前**不可测**。

## 7.2 地面以下点：一个未查明的物理不可能

真实数据点云出现 z = −498 mm。z 是 ISO 8855 的车体高度（地面为 0），所以这是**地面以下约 0.5 m** 的点，不是"相机后方"。`nf_triangulate_rays` 已经拒绝 `s≤0` 的射线，因此它不是负深度射线，而是错误视差与射线组合解出的地下点。复现稳定，与是否开 D4、是否开 σ 截断无关。本次诊断（`nfocc_run` 的 `BELOW_GROUND`）：2,077 点中 **236 点（11.4%）** 低于地面 100 mm，按来源拆分 **cam0 212 / cam1 24 / cam2 0 / cam3 0** —— 集中在前向路径，侧向 SGBM 没有贡献。这比"全局负 z"更能定位；下一步查前向径向匹配的对应点与地面交点。在有真值之前，先把 `z < −100 mm` 的点计数，不要直接硬过滤——硬过滤会把真实坡道一起切掉。

## 7.3 FORWARD 性能

11.2 s/帧，超预算 56 倍。当前实现是逐像素标量搜索，未做降采样/金字塔/并行。这是纯工程问题，不是算法问题；但在修好之前，真实直行数据只能离线跑。

## 7.4 双基线不判方向

状态机只按 `|t|` 判，直行 b≥500 mm 时强制 STEREO，SGBM 结构性失效，46,821 次插入全部越界、最终 0 点。默认门控反而正确（FORWARD，2,077 点）。修法是加方向判据，或只对侧向相机启用状态机。

## 7.5 车身掩码

矩形投影占位：MVL 76.6%、MVR 77.3% 画面被判为车身，FV 只有 0.1%。结果是"该挖的没挖，不该挖的挖了"，负对照只差 12 点。需要由标定式视图掩码替代（TODO-1），不能用矩形投影。

## 8.6 复核方法与口径

为避免"用旧缓存测新代码"，本轮按固定顺序执行：

1. **重配构建**：`cmake -S . -B build/host -DNF_WITH_VCAM=ON`，确认 `NF_WITH_VCAM=ON` 后再 `ctest`。旧目录里 OFF 的缓存会多失败 5 项，且失败信息看起来像相机/几何代码坏了。
2. **延时取逐帧值**：用 `nfocc_run --stats` 的逐帧打印，分别记录"有效帧"与"3 帧摊薄"，不用单一平均值代替。3429 ms 与 11.2 s 的差异全部来自这个口径。
3. **规模与测试取命令输出**：代码规模用 `wc -l`（src/include 分开），测试数用 `ctest -N` 与逐用例输出，文档数用 `docs_check.py` 的输出；不引用旧报告里的数字。
4. **图表与正文同源**：15 张 SVG 由 `tools/report_v2/build_figures.py` 生成，正文数字与图内常量来自同一批实测值；改数后重跑构建脚本即可，不需要手工改图。

# 九、结论与下一步

NFOCC 的工程完成度不低：4 路真实数据能进、能出点云、能出 zMap，21 个测试目标覆盖了几何、相机、体素、聚类、IO、并发与两个端到端场景，核心库只依赖 vcam 静态库、可交叉编译。三条测距/防御/精简链路都有独立的负对照，不是"看起来能跑"。

但它现在还不是一个可交付的感知系统，原因只有一个：**精度没有被证明**。`depth_accuracy` 四段全败，真实数据又无真值；FORWARD 还超预算 56 倍；地面以下点未查明；D1 掩码基本无效。这些不是"再调调参"能解决的，需要按下面的顺序做。

**P0：让精度可测（1 周）。** 合成场景换随机相位纹理，先修好 FV/RV 视口构建，再重跑六视口探针，要求 σ_d 从 14–42 px 降到 <2 px；端到端按距离分档复测，确认失败是场景还是算法。这一步不做，后面的调参都是在拟合噪声。

**P1：修 FORWARD 性能（1 周）。** 降采样 + 粗到精搜索 + 行并行，目标 <200 ms。当前 11.2 s 的量级说明有 50 倍空间，不需要改算法。

**P2：查地面以下点（3 天）。** 在三角化/前向解算后加 `z < −100 mm` 计数与 `|P|` 范围断言，定位是视差越界、射线方向错误还是体素质心漂移；同时把"网格外插入"单独计数，避免 `num_points_per_cam` 虚高。

**P3：换车身掩码（1 周）。** 用标定式视图掩码替代矩形投影，要求车头覆盖、侧视不过挖；负对照从"差 12 点"变成"该剔的剔、该留的留"。

**P4：上板与在线校准（后续）。** RK3588 / M57 实测、INT8 量化、模型引擎接入；在线自校准（地平面单应 + IMU）解决悬挂俯仰与打滑导致的基线漂移。
