## 一、先看数据规模（这决定算法选型）

| 项 | 实测值 |
|---|---|
| 单相机串行产出 | 220 点/帧 |
| 6 视口全开（估） | ~1320 点/帧 |
| 体素网格 | 9000×7500×2000 mm |
| 体素 50 mm | 有值区约 54k 格 |
| 体素 100 mm | 有值区约 6.8k 格 |
| 帧率 | 5 Hz（200 ms 预算） |
| 已用预算 | 35.5 ms（单相机），余 ~165 ms |

**关键判断：1320 点/帧的量级非常小。** 这意味着：

- 不需要 KD-Tree、不需要 GPU、不需要八叉树；
- **O(N²) 暴力邻域搜索在 N=1320 时只要 1.7M 次距离计算，约 2 ms**，完全可接受；
- 复杂的数据结构在这个规模下是负优化（构建开销 > 查询收益）。

这一点很重要：很多聚类方案是为 KITTI 那种 10 万点/帧设计的，
直接搬过来会引入不必要的复杂度。

## 二、聚类算法选型

### 候选对比

| 算法 | 复杂度 | 需参数 | 对密度不均的适应性 | 适合本场景 |
|---|---|---|---|---|
| 欧式聚类 + BFS | O(N²) 暴力 / O(N log N) KD | 半径 r | 差（固定 r） | **推荐**，N 小 |
| DBSCAN | 同上 | eps, minPts | 中 | 可选 |
| 体素连通域 | O(N) | 无 | 好（体素自适应） | **推荐**，已有网格 |
| 层次聚类 | O(N³) | 无 | 好 | 不可行 |
| Mean Shift | O(N²) 迭代 | 带宽 | 好 | 太慢 |

### 推荐：体素连通域 + BFS

**理由**：

1. **已经有体素网格**，不需要额外建索引；
2. 26 邻域连通标记是 O(N)，N 是**有值格数**（6.8k @100mm）而不是点数；
3. 无参数（连通性由体素尺寸隐含），不需要调 eps；
4. 核心库禁 STL 容器，BFS 队列可以用预分配的 `nf_i32` 数组实现。

**唯一参数是体素尺寸**，而这已经在 `NF_G_VOX` 里定了。

**已知缺陷**：两个靠得很近但不相连的物体会被合并（如紧贴墙的车）。
缓解：聚类后做一次**凸性检查**（包围盒填充率 < 阈值则拆分），
或改用区域生长（限定法向一致性）。

**这一条是我基于原理的判断，没有文献验证该策略在本场景的实际效果。**

## 三、动静分离方案

这是难点。可选路线：

### 路线 1：点级速度（基于已有体素 CMA）

**原理**：体素表已有 `n_eff`（有效观测计数）和质心。若是静止物体，
多帧观测落在同一体素，质心稳定；若是运动物体，质心逐帧漂移。

```
对每个聚类 C:
  1. 取 C 内各体素在 t-1 帧与 t 帧的质心
  2. 匹配（最近邻）
  3. v = (c_t - c_{t-1}) / Δt
  4. |v| < v_thresh -> 静止
```

| 项 | 评估 |
|---|---|
| 需要外部支持 | **无**，纯用已有的体素质心历史 |
| 额外存储 | 每体素存上一帧质心，约 6.8k × 12 字节 = 82 KB |
| 精度 | 取决于质心稳定性，静态场景可达 cm 级 |
| 失效 | 自车运动未补偿时会全判为运动；遮挡后重新出现会误判 |

**必须先补偿自车位姿** —— 这又依赖双基线/自校准提供的位姿。
所以动静分离的输入质量，取决于位姿质量。

### 路线 2：场景流（scene flow）

**原理**：用相邻帧的稠密光流 + 深度，直接算每个像素的 3D 运动矢量。

| 项 | 评估 |
|---|---|
| 精度 | 高 |
| 计算量 | 大（稠密 3D 流），估算 30–50 ms |
| 依赖 | 稠密光流 + 深度 + 位姿 |
| 本工程现状 | 无稠密光流模块 |

**不推荐作为第一版**，计算量和依赖都太重。

### 路线 3：栅格占据变化（occupancy change）

**原理**：比较 t 与 t-1 的占据栅格，新占据的格子 = 可能有运动物体进来。

| 项 | 评估 |
|---|---|
| 计算量 | O(格数)，极小 |
| 精度 | 粗（格子级） |
| 适合 | 快速筛查，不适合精确速度 |

**可作为路线 1 的补充**，用于快速标记"这一帧哪里变了"。

### 推荐组合：路线 1 为主 + 路线 3 做快速筛查

```
占据变化 -> 找出候选变化区域（O(N)，1 ms）
   ↓
只在候选区域内做点级速度估计 -> 省掉全图匹配
   ↓
聚类级投票：区域内多数点运动 -> 整个聚类判为动态
```

## 四、必须正视的三个问题

### 问题 1：220 点/帧太少，聚类意义有限

当前产出 220 点/帧（单相机）。**220 个点聚不出有意义的物体**——
一辆车在 5 m 处约占 50 个体素（100 mm 体素），220 点里可能只有十几个
落在那辆车上。

**这说明：聚类的价值取决于点云密度。** 而点云密度又取决于精度问题
（现在 σ_d 是 14–42 px，大量点被剔除）。

**所以顺序应该是：先修精度 → 点密度上来 → 聚类才有意义。**
现在做聚类，只能验证"算法能跑通"，不能验证"能分出物体"。

### 问题 2：核心库禁 STL，实现要自己写容器

`-fno-exceptions -fno-rtti` 且期望不用 STL。BFS 队列、邻域表、
聚类结果数组都要预分配 `malloc`。这不是难点，但**不能直接抄开源实现**
（都是 `std::vector` 满天飞）。

### 问题 3：动静分离依赖位姿，位姿依赖上游

见 `PLAN-DEFENSE-INTEGRATION.md`：当前上游只有帧间位移标量，
没有带姿态的绝对位姿。**动静分离的第一个输入就是位姿**。

## 五、方案对比与建议

| 方案 | 计算量 | 参数 | 依赖 | 建议 |
|---|---|---|---|---|
| 体素连通域 | ~1 ms | 无 | 已有网格 | **采用** |
| 欧式 BFS | ~2 ms | 半径 r | 无 | 备选 |
| DBSCAN | ~2 ms | eps, minPts | 无 | 不必要 |
| 点级速度 | ~3 ms | 速度阈值 | 位姿 | **采用** |
| 栅格变化筛查 | ~1 ms | 无 | 无 | **采用**（前置） |
| 场景流 | 30–50 ms | 多 | 光流+位姿 | 后续 |

**总计算量约 5 ms**，相对 165 ms 余量很宽裕。

## 七、我的判断

**技术上可行，但现在不是最佳时机。** 理由：

1. 当前 220 点/帧，聚类分不出物体，做了也只能验证"代码跑通"；
2. 动静分离依赖位姿，而位姿依赖上游（未解决）；
3. 精度问题（σ_d 14–42 px）没解决前，点云质量不足以支撑目标级输出。

**建议顺序**：先做 P0（让精度可测）→ 点密度上来 → 再做 C1/C2（聚类）
→ 位姿问题解决后做 C4/C5（动静分离）。

若你希望**先看到聚类框架跑通**（哪怕点数少），C1/C2 可以做，
约 5 天，能出可视化结果，但不应对"能分出物体"有期待。
