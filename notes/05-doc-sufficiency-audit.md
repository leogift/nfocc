# 文档充分性审计：能否据此生成完整工程？

**结论：不能。** 现有 `doc/`（3 份，54 KB）+ `docs/`（13 份，99 KB）足够定义
**几何内核 + 视差引擎 + 基线状态机**这三块，并且每块都能逐函数验收；
但**体素融合、防御层、位姿接入、工程骨架**四块的"可实现定义"缺失，
按现在的文档写代码，这四块只能靠实现者自行发明——那样产出的就不是"按文档实现"，
而是"实现者写了一份新设计"。

## 二、七个硬缺口（按严重度）

### G-1 CMA 质心融合 —— 完全没有定义

**现状**：`SPEC-ICD` 只在函数清单里写了"哈希插入/CMA 更新"，
`SPEC-VERIFY` 有一条"质心漂移 < 1 mm（CMA 正确）"。**公式、权重、饱和策略全部缺失。**

**必须补的**：
1. 更新式：`p̄ ← p̄ + (p − p̄)/(n+1)`，还是置信度加权 `n ← n + w_conf`？两者结果不同。
2. `w_conf` 从哪来：视差的置信度？还是 `1/σ_Z²`？后者与"体素存 10 字节"的内存预算冲突（要存协方差）。
3. 计数饱和：`n` 到多少封顶？不封顶则旧观测权重趋零，无法适应场景变化；封顶则要定义衰减。
4. 体素跨越：点落在两个体素交界时，只进一个（硬边界）还是按距离分摊（软指派）？
5. `sigma_cm` 怎么更新：取最小、平均、还是按式 `σ² = σ₁²σ₂²/(σ₁²+σ₂²)` 逐次融合？

**影响**：这五项每一项选错，V-VOX-2 都会"通过"但结果不同（漂移 < 1 mm 是弱判据，测不出策略差异）。

### G-2 zMap / zIndex 压缩 —— 只有结构体，没有算法

**现状**：`NFGridOutput` 有 `zmap`、`zindex` 两个字段和一句"前缀和"。
**没有一个可执行的构造流程**：体素表（哈希）→ 点云数组（排序）→ zindex（前缀和）→ 下游寻址。

**必须补的**：
1. 排序键：按 `(iy, ix, iz)` 还是 `(ix, iy, iz)`？下游 O(1) 寻址的公式依赖这个顺序。
2. 空柱体怎么表示：`zindex[i] == zindex[i+1]`（零长度）还是 `zindex[i] = 0xFFFFFFFF`（哨兵）？
3. `zmap` 的层索引与 `iz` 的对应，以及 `iz` 反向（`Z_MIN` 起）时 bit 顺序是否要翻。
4. 点数超 `MAX_POINTS=15000` 时的截断会不会破坏 `zindex` 前缀和性质。

### G-3 车身 ROI 掩码 —— 原始文档有，我的 docs 丢了

原 `doc/1` 的 `nfocc_car_body_roi_array.h` 是"标定的车身多边形，在 LUT 阶段把穿过车身的射线标为不可见"。
我的 `docs/` **完全没提这一层**。缺了它，车身钣金和外后视镜会稳定产生环状伪点云。

**必须补的**：多边形在哪个坐标系（图像？相机？车辆？）、存成什么格式、
在 LUT 构建时怎么判定射线是否穿过（3D 多边形 vs 射线求交）、膨胀像素数。

### G-4 双向光流遮挡检测 —— 同上，丢了

原 `doc/1` §5.2 有 `dof.cpp`、`nOcclusion=14`。我的 `docs/` 只字未提。
缺了它，遮挡边界会产生"假深度边缘"。

**必须补的**：光流怎么算（在展开图上还是原图上）、双向一致性的判据式、
`nOcclusion` 是硬阈值还是软权重（原 doc2 建议软权重）、与视差置信度怎么合成。

### G-5 FoE 过滤 —— 提了原理，没给实现

我在 `SPEC-EPIPOLAR` 提了 FoE 退化，但没有：
锥的定义（apex 在哪、张角多少）、判据式、是逐相机还是逐体素（我指出过应该逐相机，但没定规范）、
与基线状态机 `ROTATION_ONLY` 的边界在哪。

### G-6 位姿接入 —— 完全缺失

`NFPose` 有 `R_cv` 和 `t`，但**没有任何文档说明它们从哪来**：
轮速脉冲 + 陀螺零偏 + IMU 积分 → 车辆位姿 → 相机位姿的变换链，一步都没有。
两帧之间是"直接用里程计位姿相减"还是"累积积分"，误差特性完全不同。

**这一条最致命**：整个运动双目依赖基线的准确值，而基线 = 位姿差分。
文档定义了"用 `t_rel`"，却没定义 `t_rel` 怎么来的。

### G-7 工程骨架 —— 全部缺失

| 项 | 状态 |
|---|---|
| 语言与标准 | 未定（C / C++ / Rust？C99 还是 C++17？） |
| 构建系统 | 未定（CMake / Bazel / Make） |
| 目录结构 | 未定 |
| 线程模型 | 未定（4 路相机并行？引擎与体素流水？） |
| 内存分配策略 | 未定（启动时全分配 / 池化 / 按需） |
| 日志与故障上报 | 未定 |
| 与下游的传输（SERL/共享内存） | 只在原 doc 提到，我的 docs 没有接口 |

## 三、还有三个"看似有、其实不够"的项

### G-8 视口 LUT 的非均匀栅格

`SPEC-EPIPOLAR` §3.3 说"视口重排后每行有效宽度不同"，`SPEC-ICD` 有 `valid_x0[y]` 字段。
但**没有定义 LUT 的存储布局**：每个栅格点存什么（鱼眼 u,v 各几分位）、
无效点是 `(0,0)` 还是靠 mask、Q12.4 超出 ±2048 怎么处理。

### G-9 体素 Hash 的插入细节

`SPEC-COORD` §5.3 定了位拼接，但没定：
哈希表的容量（81000 个格子全开 vs 稀疏）、开放寻址的探测策略、负载因子阈值、
超限时的丢弃策略（我在 `NF_E_VOXEL_FULL` 里提了错误码，没给策略）。

### G-10 内存预算只覆盖了 SGBM

`PARAM` E.1 只算了单路 SGBM 的 cost volume。**全链路实算**（1920×1536 原图，视口 downscale=2 即 960×768）：

| 项 | 大小 | 说明 |
|---|---|---|
| 4 路原图 | 11.80 MB | 单 Y，单缓冲 |
| 4 路视口图 | 2.95 MB | 960×768 |
| 4 路视差图 | 26.54 MB | float disp + u8 valid + float conf |
| 体素表 | 0.81 MB | 81000 × 10 B |
| 输出点云 | 0.14 MB | 15000 × 9 B |
| **SGBM cost volume** | **377.49 MB** | `numDisp=256 @960×768`，**单路** |
| 合计（4 路串行） | **约 420 MB** | 一次只算一路 |
| 合计（4 路并行） | **约 1.93 GB** | 4 × 377 MB + 其余 |

**这个数直接决定线程模型**：
- RK3588（4–8 GB 板）：4 路并行 1.9 GB 可行但挤，串行 420 MB 宽裕。
- Axera M57：需按实际可用内存核实，**并行很可能不可行**。
- SGBM cost volume 是唯一的大头，它决定了"能不能并行"。

这条缺口不补，工程师会自然地写成"4 路并行"（因为 4 路相机直觉上该并行），
然后在板端撞内存墙——而且是在集成后期才撞。
