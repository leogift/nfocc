# 视差引擎候选评估

结论先行：**三份文档把视差引擎当成"选一个算法"的问题，实际是"选一个能装下 100–200 px 视差、
且能表达无效区"的工程问题。** 按这个标准筛，现有三个候选没有一个是现成可用的。

---

## 候选 1：OpenCV StereoSGBM（doc3 的 L0 保底方案）

**可用，但不是"开箱即用"**。已实测（`tools/sgbm_bench.py`，1280×720，真实视差 180 px，CPU）：

| numDisparities | 中位视差 | 正确? | 有效覆盖 | 耗时 |
|---|---|---|---|---|
| 64 / 128 | 26 / 91 | NO（误差 89–154 px） | 6% / 2.5% | 31–34 ms |
| 192 | 180.0 | yes | 98.9% | 32 ms |
| 256 | 180.0 | yes | 93.1% | 50 ms |
| 512 | 180.0 | yes | 69.8% | 59 ms |
| 1024 | 180.0 | yes | 23.2% | 48 ms |
| 2048 | — | OOM | — | — |

三条**必须写进整定表**的规律：
1. `numDisparities` 单位是**像素**（`compute()` 返回 CV_16S，÷16 得像素值）。doc3 §4.3 的"128 即 8px"是错的。
2. 容量 < 真实视差 → 完全失效，不是精度差一点。容量刚好等于真实视差时误差为 0。
3. **有效覆盖 = (W − numDisparities)/W**，实测无效列恰好是最左侧 `numDisparities` 列。
   开 512 损失 40% 图像宽度。近场要大视差预算与保住图像宽度直接冲突。

它原生带的、DispMap 缺的两样东西，在 NFOCC 里都有用：`disp12MaxDiff`（左右一致性）、
`speckleWindowSize/Range`（小连通域过滤）、`mode=XY_SUB`（亚像素）。
这三项正好对应 doc1 §5.2 的双向一致性检测的工程实现。

**平台适配**：CPU 上 1280×720/192 px 约 32 ms（M 系列单线程）。ARM A72 单核 NEON 上按 5–8× 估
约 160–260 ms，**与 doc3 要求的 15 ms 差一个数量级**。doc3 §1.3 的"SGBM 单帧 ≤15 ms（1080p，A72 单核 NEON）"
在没有硬件加速的前提下不成立。这需要用 NEON 实测或换 ASIC/GPU 才能验。

## 候选 2：DispMap（工作区 `stereodisp`，自研）

已逐行核实（不是读 README）：

| 项 | 事实 | 依据 |
|---|---|---|
| 输出语义 | 像素视差（非归一化、非深度），cost volume + soft-argmin | `dispmap/models/head/disp_head.py:37-40` |
| 视差上限 | `max_disp = 96`，cost_agg_stride=4 → 实际只有 24 个 bin，等价 1/4 像素栅格 | `exps/dispmap_m_regnet_x_400mf.py:25`；`disp_head.py:38-39,44-46` |
| 符号 | **只支持 d ≥ 0**，`for i in range(max_disp)` + `right[:,:,:,:-i]`，无负视差通道 | `dispmap/models/neck/cost_volume_neck.py:28-34` |
| **亚像素** | **无**。`return disp.to(torch.int32)` 在推理时强制截断 | `disp_head.py:51-52` |
| **无效区** | **无**。无置信度、无遮挡 mask、`forward_export` 只返回单张量 | `disp_head.py:46`；`dispmap.py:119-121` |
| 输入尺寸 | config 写死三套 (384,384)/(352,576)/(736,256) | `exps/*.py:24` 等 |
| 基线与标定 | 代码中搜不到 baseline/focal/rectify 任何关键词 | 全仓 grep |

**结论：不能作为 NFOCC 的近场视差引擎。** 96 px 上限对 100–200 px 的真实视差差 2 倍，
且无亚像素、无无效区——这两点恰好是 NFOCC 双基线验证与 CMA 加权的前提。

若要用，必须三件事同时做：`max_disp` 提到 ≥320、加负视差/无效 mask 分支、删掉 int32 截断。
**这已经不是"改配置"，是改模型结构与训练流程**。加上重训数据（InStereo2K 是室内静态微基线，
与近场 40–500 mm 运动基线不同分布），成本高于直接用 SGBM。

有价值的部分：它带 RKNN 导出链路（`onnx2rknn.py`），如果将来要上 NPU 做**学习式**视差，
这条链路可以复用。但那时得是重新设计的网络，不是这个。

## 候选 3：StereoNetPlus（doc3 的 L1 升级档）

**未能核实**。调研子任务在 arXiv / Semantic Scholar / OpenAlex 上都没拿到可引用的原文与指标，
只拿到 429 与反爬页面。因此 doc3 §4.1 关于它"有效工作范围 5–90 m"的说法我**无法证实也无法证伪**。

在没有原文的情况下，可以确定的是几何约束：**它同样基于 cost volume 与水平搜索**，
所以 C12/C13 的极线重定向问题对它一样存在，doc3 把它当"更先进的引擎"解决不了极线方向问题。
这一条不依赖原文，是结构性的。

## 候选 4（文档未提）：原 NFOCC 的 TDA4 SDE

上限约 191 px（此数字来自 doc2 附录 A 的引用，其推导本身有误——见 01-numcheck C3，**数字出处待核实**）。
即使 191 px 成立，对 100–200 px 的近场视差**刚好卡在边界**，大基线档位仍然装不下。
这也解释了为什么原 NFOCC 用双基线：单档基线在 SDE 的 191 px 里做不了 0.5–5 m 全覆盖。

## 我的建议

**P2 阶段用 SGBM 起步**，因为它是唯一"现在就能跑、且有原生无效区表达"的选项。
但必须同时接受两件事：
1. 极线重定向（`notes/02-decisions.md` S1）先做，否则侧相机根本不能用；
2. 分档基线，`numDisparities` 每档按 `f·b/Z_min` 反推，不要用一个值覆盖 0.5–5 m。

**不要**在 P2 阶段引入 DispMap 或 StereoNetPlus。两者都需要"重新设计 + 重训 + 换指标"，
放在 P2 会让整条链路无法按期验收。若将来要上学习式视差，单独开一个 P6，用 P2 产出的
SGBM 结果做蒸馏基线，而不是从预训练权重起步。
